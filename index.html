Testes

Quando usar cada teste

Teste de Caixa Branca Quem conhece o código

O que faz

Testa o funcionamento interno do sistema, com acesso ao código-fonte. Quem testa escolhe as entradas olhando a lógica: cada condição, cada ramo de um if, cada laço, cada caminho possível. O objetivo é garantir que todas as partes do código foram executadas e se comportam como deveriam.

Quando usar

Durante o desenvolvimento, em testes unitários e de integração, para medir cobertura de código, encontrar trechos nunca executados e validar regras complexas de cálculo ou permissão.

Teste de Caixa Preta Sem ver o código

O que faz

Testa o sistema pelo lado de fora, como um usuário, sem olhar o código. Quem testa só conhece as entradas e as saídas esperadas, definidas nos requisitos e na documentação, e verifica se o resultado na tela corresponde ao que foi pedido.

Quando usar

Na homologação de entregas, na validação de requisitos e critérios de aceite, e em testes de sistema e aceitação. É o tipo mais usado no fluxo de QA do Conecta.

Outros testes recomendados

Do nível do código à experiência de quem usa.

Teste de Caixa Cinza Mistura das duas

O que faz

Testa pela interface, como na caixa-preta, mas com algum conhecimento interno: rotas da API, estrutura do banco, regras de permissão ou as requisições de rede da página.

Quando usar

Para investigar bugs e escrever relatórios precisos, indicando qual requisição falhou e com qual status. É a abordagem do mini-qa-harness.

Teste Unitário Caixa branca

O que faz

Verifica a menor parte do código, como uma função ou um componente, isolada do resto.

Quando usar

A cada mudança de código, rodando automaticamente antes do merge.

Teste de Integração Caixa branca ou cinza

O que faz

Verifica se módulos e serviços funcionam juntos: frontend com API, API com banco, sistema com serviços externos.

Quando usar

Quando duas partes passam a se comunicar ou quando um contrato entre elas muda.

Teste de API Caixa preta ou cinza

O que faz

Valida requisições e respostas: status, formato dos dados, mensagens de erro e permissões por perfil.

Quando usar

Quando um endpoint é criado ou alterado, antes mesmo de a tela estar pronta.

Teste de Sistema (ponta a ponta) Caixa preta

O que faz

Percorre um fluxo completo do usuário, do login ao resultado final, com o sistema inteiro rodando.

Quando usar

Em fluxos críticos, como enviar uma prestação de contas do início ao fim.

Teste de Aceitação Caixa preta

O que faz

O cliente ou responsável pelo negócio confirma que a entrega atende aos critérios de aceite.

Quando usar

Antes de uma entrega ir para produção.

Smoke Test Caixa preta

O que faz

Checagem rápida de que o essencial funciona: o sistema abre, o login entra, as telas principais carregam.

Quando usar

Logo após cada deploy, antes de qualquer teste mais longo.

Teste de Regressão Caixa preta

O que faz

Repete testes que já passaram para garantir que uma mudança nova não quebrou o que funcionava.

Quando usar

Após correções e novas funcionalidades, principalmente em telas próximas da alteração.

Reteste Caixa preta

O que faz

Executa de novo o caso que falhou para confirmar se o defeito foi corrigido.

Quando usar

Quando a issue chega em Pending Retest no ciclo de vida do bug.

Teste Exploratório Caixa preta ou cinza

O que faz

Quem testa investiga livremente, guiado por um objetivo, criando os próximos passos conforme observa o sistema.

Quando usar

Em funcionalidades novas, telas com pouca documentação ou para achar bugs que roteiros não preveem.

Teste de Usabilidade Caixa preta

O que faz

Avalia se a tela é fácil de entender e usar: clareza dos textos, mensagens de erro, consistência e esforço para concluir a tarefa.

Quando usar

Em toda Task que produz telas, no Desktop e no Mobile.

Teste de Acessibilidade Caixa preta ou cinza

O que faz

Verifica se pessoas com deficiência conseguem usar o sistema: contraste, navegação por teclado, leitor de tela e textos alternativos, seguindo a WCAG.

Quando usar

Em toda Task que produz telas.

Teste de Compatibilidade e Responsividade Caixa preta

O que faz

Confere o sistema em navegadores, sistemas e tamanhos de tela diferentes.

Quando usar

Em telas novas ou alteradas, sempre no Desktop e no Mobile.

Teste de Desempenho Caixa preta ou cinza

O que faz

Mede tempo de resposta e estabilidade sob muitos usuários (carga), além do limite (estresse) ou por longos períodos.

Quando usar

Antes de prazos com muito acesso, como encerramento de editais e prestações.

Teste de Segurança Caixa preta, cinza ou branca

O que faz

Procura vulnerabilidades e acessos indevidos: um perfil vendo ou alterando dados de outro, dados expostos, entradas maliciosas.

Quando usar

Em funcionalidades com permissões, dados pessoais ou financeiros.

Nomenclatura

Termos usados no dia a dia de QA, segundo a terminologia do ISTQB.

Erro, Defeito (Bug) e Falha Causa e efeito

Os três formam uma cadeia: o erro gera o defeito, que gera a falha.

  1. Causa humana

    Erro

    ou engano

    Uma ação humana equivocada de quem desenvolve, analisa ou escreve o requisito.

  3. No produto

    Defeito

    ou bug

    A imperfeição deixada pelo erro no código, no requisito ou no protótipo.

  5. Na execução

    Falha

    o que o usuário vê

    O comportamento errado quando o sistema roda, diferente do esperado.

  • Nem todo defeito gera falha. Se o trecho nunca é executado, o defeito fica adormecido.
  • Nem toda falha vem de defeito. Ela pode ter causa no ambiente, como um storage mal configurado.
  • No dia a dia do QA: o teste observa a falha e registra o defeito na issue com a tag QA New.

Tags

No GitHub Projects, as Tasks recebem tags para organização das demandas e posterior análise de dados.

Quando usar cada tag

QA New
Defeito identificado e cadastrado pela primeira vez.
QA Assigned
Defeito é atribuído para um Dev avaliar.
QA Open
Dev inicia análise e correção.
QA Fixed
Dev finaliza a correção.
QA Pending Retest
Em espera do time de teste verificar.
QA Retest
Em execução do reteste.
QA Verified
Defeito corrigido.
QA Close
Defeito corrigido, testado e aprovado.
QA ReOpened
Defeito não corrigido.
QA Duplicate
Defeito já encontrado antes e verificado em outra Task.
QA Deferred
Defeito será corrigido em versões futuras.
QA Not a Bug
Dev verificou e não era um defeito.

Workflow

Por onde passa o trabalho de QA

  1. Coluna

    Homologation

    Testar as entregas que estão nesta coluna.

  3. Subissue

    Teste de QA

    A partir da issue existente, criar uma subissue de QA atrelada a ela e realizar o teste.

  5. Tudo certo

    Done

    A issue vai para a coluna Done.

    Algo a verificar

    Desaprovado

    A issue vai para a coluna Desaprovado.

Funcionalidades

O teste analisa os requisitos e a documentação. Se faltar alguma informação nesses locais, abra uma Task para incluir o que faltar.

Telas

Toda Task que produz telas passa por teste de usabilidade em três frentes:

  • Desktop
  • Mobile
  • Acessibilidade

Atenção a cenários e mensagens de erro

Regra: a mensagem diz qual é o erro e o que o usuário deve fazer. Evite mandar o usuário entrar em contato.

Etapas de um teste com agentes

Da leitura da issue à limpeza do ambiente. Os agentes testam; uma pessoa decide o que é publicado.

  1. 01

    Ler a issue

    Copiar os critérios de aceite sem parafrasear.

  2. 02

    Checar o ambiente

    Versão no ar, migrations, flags e dados de teste.

  3. 03

    Validar perfis

    qa smoke entra com cada perfil necessário.

  4. 04

    Disparar testadores

    Agentes em paralelo, dois ou três casos cada, 15 minutos.

  5. 05

    Verificar achados

    Conferir telas, rede e trace; descartar falhas de ambiente.

  6. 06

    Registrar

    Gravar a reprodução com trace do Playwright e, se quiser, Jam.

  7. 07

    Revisar e publicar

    Rascunho aprovado por uma pessoa antes de ir para o GitHub.

  8. 08

    Limpar

    Apagar pela interface os dados com prefixo de teste.
